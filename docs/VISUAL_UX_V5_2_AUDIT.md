# 4Chinese V5.2 Visual UX Audit

Date: 2026-10-06  
Source baseline referenced by the capture plan: 0.1.33, Android versionCode 35.  
Evidence device: Pixel 2 Android emulator, API 36, 1080×1920, 420 dpi, font scale 1.0. This is one Android emulator configuration, not a release certification.

## Coverage and evidence boundaries

- Current inventory: 62 .tsx files under src/app, of which 60 are route screens and 2 are layout files (_layout.tsx). The route inventory was compared with artifacts/ui-audit-2026-10-06/capture-manifest.csv: all 60 route sources match one unique manifest row; no missing or extra routes.
- Screenshot inventory: 82 PNGs under artifacts/ui-audit-2026-10-06/screens/: 60 manifest route captures, onboarding-goal-step.png, and 21 probe-*.png supplemental captures. Five contact sheets are available at artifacts/ui-audit-2026-10-06/contact-sheet-01.png through contact-sheet-05.png.
- Capture boundary: these screenshots are the pre-V5.2 UI baseline. They have not been regenerated after the implementation edits described in the current final report; use them as comparison/source-audit evidence, not as visual approval of the updated build.
- Source inspection: all 60 current route files were inventoried; route purpose, exported screen shape, primary navigation/UI patterns, and available accessibility annotations were inspected. This is a visual/route audit, not a full line-by-line correctness, security, or business-logic review.
- Visual/manual inspection: all 60 routes were opened/captured in the emulator according to the capture manifest, and the five contact sheets were visually reviewed. Selected high-risk images (onboarding, exam session/result, AI speaking, Reader, story detail, invalid mistake practice, and deck editor) were also inspected individually.
- Loading/empty/error coverage: only the fixture/state named in each row was captured. Loading, empty, and error variants were not systematically forced for every route. A redirect or empty-state screenshot is not evidence that the populated interaction passed.
- Dark mode: not tested across the route set.
- Accessibility: source annotations were inspected where present, but TalkBack, focus order, announcements, contrast measurements, switch access, and the complete accessibility tree were not manually certified. Accessibility findings below are review targets, not claims of conformance.
- Motion/performance: no route-wide reduced-motion toggle, animation stress test, or frame-time/profile run was performed. Routes using animation still need runtime verification under reduced motion.
- Other untested environments: font scales other than 1.0, small/large physical devices, Android versions other than API 36, iOS, and offline/online service failure paths are not covered by these captures.

## Visual system assessment

The source now defines presentation-only mode recipes and route classifications in `src/theme/visual-modes.ts`, with limited call sites. The mode labels below describe audit intent; they are not persisted settings, universal wrappers, or proof that every route was rethemed or tested.

- LEARN: guided progress, orientation, and useful feedback; reserve celebration for meaningful milestones.
- REVIEW: low-distraction retrieval practice and clear answer/result feedback.
- READ: calm, content-first reading with legible Chinese text and reading-position continuity.
- EXAM: quiet, neutral assessment presentation; state clearly when content is unverified practice rather than an official exam.
- UTILITY: settings, search, management, and service workflows.

The baseline screenshot set suggests a consistent blue-and-light-surface foundation, but several pages repeat the screen title in both the navigation header and page body. In the captured baseline, the onboarding footer overlaps HSK 5/6, and story detail exposes the technical route label stories/[id]. Source edits in the current V5.2 pass make onboarding choices scrollable above a persistent footer and set the story route title to “Đọc truyện”; neither fix has a post-change device screenshot yet. Across the inspected light-theme captures, status-bar symbols appear very pale against the light surface; verify the system-bar style and contrast on device before treating this as a confirmed defect.

No visual overhaul should alter SRS scheduling, saved answers, progress, XP rules, deck contents, course unlock states, or local SQLite data. A screen classification of REDESIGN means visual restructuring only unless separately authorized.

## Known findings and next verification

1. P1 regression: resolve and rerun automatic exam-result navigation after submit. The prior QA plan records a native ScreenStackFragment/non-stack-container crash; the saved attempt could be reopened from history. Current source waits briefly after submission and disables the native transition for exam session/result, but that is a mitigation hypothesis until QA-06 is rerun on Android. Passing the history path alone does not close this issue.
2. P0 layout: source now keeps onboarding choices scrollable above the persistent footer. Recheck a small device and larger font scale; the baseline screenshot remains an image of the old overlap.
3. P0 visual: prioritize Learning Path, Reader, Speaking AI, learning-session feedback, and meaningful empty states. Use real persisted state/fixtures and preserve underlying business logic.
4. P1 presentation: source now sets the story detail stack title to “Đọc truyện”; capture the route again to verify it on-device. Verify the content-review route stays development-only in release builds.
5. Before claiming accessibility, dark-mode, reduced-motion, or performance completion, test those settings/devices explicitly and report actual results. None are certified by this screenshot audit.
6. Capture valid-state follow-ups are needed for Learn/Review sessions, deck quiz/listening/pronunciation, mistake practice, Reader import/read state, Cloud auth, and microphone/recording flows. Do not mark those interactions passed based on guard or empty-state screenshots.
